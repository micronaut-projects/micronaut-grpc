Micronaut gRPC

Integration between Micronaut and gRPC

Version: 5.2.1-SNAPSHOT

1 Introduction

This project allows building gRPC servers and clients with Micronaut.

Micronaut adds the following features to the gRPC experience:

  • Compile Time Dependency Injection (DI) and Aspect Oriented Programming (AOP)

  • Service Discovery and Registrations

  • Distributed Tracing

  • Cloud Native Configuration

2 Release History

For this project, you can find a list of releases (with release notes) here:

https://github.com/micronaut-projects/micronaut-grpc/releases

3 Getting Started

To get started you need first create a Micronaut project. The easiest way to do this is with the Micronaut Launch:

  • Go to Micronaut Launch

  • Select "gRPC Application" under "Application Type"

  • Choose a Language / Build System etc.

  • Click Generate

Replace java with kotlin or groovy to change language and the build flag with maven to use Maven instead.

Or alternatively you can create a project with curl:

curl --location --request GET 'https://launch.micronaut.io/create/grpc/demo?lang=JAVA&build=GRADLE' --output demo.zip
unzip demo.zip -d demo
cd demo

To manually setup gRPC you can create an application:

$ mn create-app helloworld
Add --lang kotlin or --lang groovy to create a Kotlin or Groovy application and --build maven to use Maven instead of Gradle.

Then follow the below steps depending on the build system and language chosen. The Gradle examples are shown for both the Groovy DSL (build.gradle) and the Kotlin DSL (build.gradle.kts).

Configuring Gradle

The com.google.protobuf plugin registers the generated sources with the corresponding source sets, so no additional sourceSets configuration is required.

Java and Groovy Projects

For Java or Groovy projects, add the com.google.protobuf plugin to your existing plugins block:

plugins {
    ...
    id 'com.google.protobuf' version '0.10.1'
}
plugins {
    ...
    id("com.google.protobuf") version "0.10.1"
}

Then configure protobuf source generation:

def grpcVersion = '1.84.2'
def protobufVersion = '4.36.2'

protobuf {
    protoc { artifact = "com.google.protobuf:protoc:$protobufVersion" }
    plugins {
        grpc { artifact = "io.grpc:protoc-gen-grpc-java:$grpcVersion" }
    }
    generateProtoTasks {
        all()*.plugins { grpc {} }
    }
}
val grpcVersion = "1.84.2"
val protobufVersion = "4.36.2"

protobuf {
    protoc { artifact = "com.google.protobuf:protoc:$protobufVersion" }
    plugins {
        create("grpc") { artifact = "io.grpc:protoc-gen-grpc-java:$grpcVersion" }
    }
    generateProtoTasks {
        all().configureEach {
            plugins {
                create("grpc")
            }
        }
    }
}
If you are using JDK 9 or above, provide the following compiler option to the gRPC plugin to skip javax.annotation.Generated stubs: option '@generated=omit' (added in gRPC Java v1.64.0). See issue 9179 for background. 
protobuf {
    generateProtoTasks {
        all()*.plugins {
            grpc {
                option '@generated=omit'
            }
        }
    }
}
protobuf {
    generateProtoTasks {
        all().configureEach {
            plugins {
                named("grpc") {
                    option("@generated=omit")
                }
            }
        }
    }
}

Configuring Maven

For Maven create a Maven project first:

$ mn create-app helloworld --build maven

Add --lang kotlin or --lang groovy for a Kotlin or Groovy project.

4 gRPC Server

Writing a Simple gRPC Server

To implement a gRPC server for the previously defined helloworld.proto definition you first need to generate the Java stubs using Gradle or Maven then create a class that extends from GreeterGrpc.GreeterImplBase.

For example:

import io.grpc.stub.StreamObserver;

import jakarta.inject.Singleton;

@Singleton
public class GreetingEndpoint extends GreeterGrpc.GreeterImplBase { // (1)

    private final GreetingService greetingService;

    // (2)
    public GreetingEndpoint(GreetingService greetingService) {
        this.greetingService = greetingService;
    }

    @Override
    public void sayHello(HelloRequest request, StreamObserver<HelloReply> responseObserver) {
        // (3)
        final String message = greetingService.sayHello(request.getName());
        HelloReply reply = HelloReply.newBuilder().setMessage(message).build();
        responseObserver.onNext(reply);
        responseObserver.onCompleted();
    }
}

Running the gRPC Server

To run the server use the Application class or run ./gradlew run for Gradle or ./mvnw compile exec:exec for Maven.

The server by default runs on port 50051, however you can configure which port the server runs on by setting grpc.server.port to whichever value you wish (a value of ${random.port} will use a random port).

Configuring the gRPC Server

The server can be configured in a number of different ways. By default, Micronaut configures gRPC’s NettyServerBuilder via application.yml.

By default, the gRPC server will be enabled. To disable the gRPC server, set grpc.server.enabled to false.

Context Propagation

gRPC delivers each event of a call (messages, half-close, cancellation) as a separate task on the server executor, possibly on a different thread. A unary service method runs when the client half-closes the call, so a Micronaut PropagatedContext that a server interceptor makes current while it starts the call would otherwise be gone by the time the method runs.

Micronaut registers an interceptor that runs last, closest to the service, and makes that context current again for every later event of the call. A server interceptor can therefore add context elements, for example an authenticated user or MDC entries, and the service method sees them:

@Singleton
public class TenantInterceptor implements ServerInterceptor {
    private static final Metadata.Key<String> TENANT = Metadata.Key.of("x-tenant", Metadata.ASCII_STRING_MARSHALLER);

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(ServerCall<ReqT, RespT> call,
                                                                 Metadata headers,
                                                                 ServerCallHandler<ReqT, RespT> next) {
        return PropagatedContext.getOrEmpty()
            .plus(new Tenant(headers.get(TENANT))) // your own PropagatedContextElement
            .propagate(() -> next.startCall(call, headers));
    }
}

This covers interceptors registered as beans. Interceptors applied to a single service with ServerInterceptors.intercept(..) run inside Micronaut’s interceptor, so a context they make current is not carried to later events. The captured context is only a fallback: if an interceptor makes a context current around a later event, for example around one message, that context takes precedence.

To turn this off, set grpc.server.context-propagation.enabled to false.

Micronaut Security’s micronaut.security.intercept-url-map is not applied to gRPC calls. Its entries are Ant-style HTTP path patterns (such as /**), so an application exposing both HTTP and gRPC endpoints can keep its HTTP rules there and declare gRPC rules separately.

Granted roles are the roles exposed by the Authentication (Authentication#getRoles()) combined with the roles resolved from its attributes by the RolesFinder bean, so both JWT claims and authentications returned by a custom GrpcServerAuthenticationFetcher (for example Authentication.build("alice", List.of("ROLE_ADMIN"))) are matched against role-based rules.

If a rule requires authentication and no token is provided, the server responds with UNAUTHENTICATED. If a token is provided but validation fails, or the authenticated principal does not satisfy the configured access rules, the server responds with PERMISSION_DENIED.

With Micronaut Security’s default micronaut.security.reject-not-found=true, unmatched gRPC methods are rejected as well. Define explicit intercept-method-map patterns for the methods you want to secure, or set reject-not-found to false if unmatched methods should remain accessible.

Context Propagation

gRPC runs a call’s response callbacks, such as StreamObserver.onNext of an async stub, on the channel’s executor. Micronaut captures the PropagatedContext of the thread that starts the call (when ClientCall.start runs, which a stub does for you) and makes it current again in those callbacks, so MDC entries, tracing context and other context elements of the caller are available there. Client interceptors see it in their response listeners too, including calls an interceptor completes itself without reaching the server. A callback that already runs inside a propagated context keeps it.

To turn this off, set grpc.client.context-propagation.enabled to false.

For every service class that protoc-gen-grpc-java generates, the processor generates a bean factory for its stubs. You can then inject the blocking, async and future stubs with @GrpcChannel, by field or constructor:

@Singleton
public class GreetingClient {

    private final GreeterGrpc.GreeterBlockingStub greeter;

    public GreetingClient(@GrpcChannel("greeter") GreeterGrpc.GreeterBlockingStub greeter) {
        this.greeter = greeter;
    }
}

The channel is resolved and configured exactly as for an injected ManagedChannel, including grpc.channels.[NAME] configuration, interceptors and service discovery. All stubs of the same channel share one ManagedChannel. A stub of a disabled channel behaves like a disabled channel: a @Nullable or Optional injection point receives no stub.

The generated factories are secondary beans, so a stub bean you define yourself in a @Factory takes precedence. Stubs of other code generators, such as the grpc-kotlin coroutine stubs, aren’t generated and still need a factory.

Property Default Description

enabled

false

Whether the channel has a circuit breaker.

failure-threshold

5

The number of consecutive failed calls that opens the circuit.

reset-timeout

20s

How long the circuit stays open. After it, a single trial call is let through: it closes the circuit if it succeeds and opens it again if it fails. Calls made while the trial is in flight fail fast.

failure-status-codes

UNAVAILABLE, DEADLINE_EXCEEDED

The status codes that count as failures. Other codes, such as INVALID_ARGUMENT or NOT_FOUND, are application errors and reset the count.

While the circuit is open, a call ends with status UNAVAILABLE and the description Circuit breaker for gRPC channel [greeter] is open, without reaching the network. Client interceptor beans still see these calls, so tracing and metrics record them.

All stubs created from the same channel share one circuit breaker. Inject GrpcCircuitBreakerRegistry to read its state, for example in a health indicator:

CircuitState state = registry.currentState("greeter").orElse(CircuitState.CLOSED);
The circuit breaker never retries a call, because streaming calls cannot be replayed. To retry failed calls, enable retries in the channel’s gRPC service config, which applies before a call counts as failed.

Avoiding Reflection

To create a message from a request body, Micronaut needs a builder for the message type. Add the micronaut-protobuff-processor annotation processor to generate a factory for every message class compiled in your project, so that builders are created without reflection:

annotationProcessor("io.micronaut.grpc:micronaut-protobuff-processor")
<annotationProcessorPaths>
    <path>
        <groupId>io.micronaut.grpc</groupId>
        <artifactId>micronaut-protobuff-processor</artifactId>
    </path>
</annotationProcessorPaths>
[tool.pyronaut.dependencies]
build = [
    "io.micronaut.grpc:micronaut-protobuff-processor",
]

The processor brings Micronaut’s annotation processing (micronaut-inject-java) with it, so nothing else is needed on the annotation processor path. The project must have micronaut-protobuff-support on its compile classpath, directly or through micronaut-protobuff-json-support.

The processor runs on the Java sources that protoc generates. It finds message classes by the @com.google.protobuf.Generated annotation and writes a small factory for each one, which Micronaut registers like its own generated services, so GraalVM native images need no extra reflection configuration for them. The JSON support in micronaut-protobuff-json-support uses the same factories.

For compatibility, messages without a generated factory still work: Micronaut falls back to calling their static newBuilder() method by reflection. This applies to messages compiled elsewhere, for example in a shared library of .proto definitions built without the processor, and to messages in the default Java package, which the processor skips.

How this works

Controller Creation

  2. For each bean, peek into the gRPC allocated methods created.

  3. Register the bean in a cache

However, to create a json request output one can take any gRPC request protocol buffer and convert it to json using the io.micronaut.protobuf.json.ProtobufJsonTranscoder class.

Usage

/grpc-json/{serviceName}/{method}

where the serviceName is the name of the gRPC service and the method is the name of the method.

import "google/api/annotations.proto";

service LibraryService {
  rpc GetShelf(GetShelfRequest) returns (Shelf) {
    option (google.api.http) = { get: "/v1/{name=shelves/*}" };
  }
  rpc UpdateBook(UpdateBookRequest) returns (Book) {
    option (google.api.http) = {
      put: "/v1/books/{book.id}"
      body: "book"
      additional_bindings { patch: "/v1/books/{book.id}" body: "book" }
    };
  }
  rpc GetBookTitle(GetBookRequest) returns (Book) {
    option (google.api.http) = { get: "/v1/books/{id}/title" response_body: "title" };
  }
}

The rules are read from the service’s protobuf descriptors when the application starts. The module uses no reflection and needs no generated code. It supports the following:

  • The get, post, put, patch and delete methods, custom methods (custom: { kind: "…​" }, where kind: "*" matches any HTTP method unless a rule for that method also matches) and additional_bindings.

  • Path templates with literal segments, and * wildcards, variables with or without a sub-template ({name=shelves/*}), nested field paths ({book.id}) and a verb suffix (/v1/books/{id}:archive).

  • body: "", body: "<field>" or no body. When the body is not , query parameters set the remaining fields. Query parameters may use proto field names or JSON names, including nested paths like paging.token, and a repeated field takes repeated parameters. A field bound by the path or the body is not overridden by a query parameter, whichever name the parameter uses.

  • response_body, which returns a single field of the response instead of the whole message.

A request is matched against the rules before routing. Requests that match no rule continue to your controllers. A matching request is dispatched in-process to the gRPC service, through the ServerInterceptor beans of the application. The HTTP request headers become gRPC metadata, except for hop-by-hop and transport headers, grpc-* headers and binary (-bin) headers. Interceptors that authenticate from metadata therefore also apply to REST calls.

The request and response bodies use the protobuf JSON mapping. When a call fails, the gRPC status is mapped to an HTTP status in the same way as Google APIs: INVALID_ARGUMENT becomes 400, NOT_FOUND becomes 404, UNAUTHENTICATED becomes 401, and so on. The body has the following form:

{"error": {"code": 404, "message": "Shelf not found", "status": "NOT_FOUND"}}

A request body that is not valid JSON, or that does not match the request message, is rejected with 400.

The following are not supported:

  • Streaming methods: rules on client, server or bidirectional streaming methods are skipped with a warning.

  • google.protobuf.Any fields, because no type registry is configured.

  • Unknown query parameters are ignored, not rejected.

Unlike the /grpc-json endpoints described above, transcoding does not use the @GrpcRestJsonExposed annotation. It exposes only the methods annotated with google.api.http, with the paths and HTTP methods those annotations define.

Endpoint Shape

Unary gRPC-Web requests are served from:

/grpc-web/{serviceName}/{method}

For the sample GreeterService#sayHello method this becomes:

http://localhost:8080/grpc-web/GreeterService/sayHello

The path prefix defaults to grpc-web and can be changed with:

micronaut:
    grpc:
        web:
            path: custom-grpc-web

Supported Content Types

The endpoint accepts the following media types, ignoring case and parameters, and answers with the media type of the request:

  • application/grpc-web and application/grpc-web+proto

  • application/grpc-web-text and application/grpc-web-text+proto

Binary requests use the standard gRPC-Web frame format. Text requests use the same frames, base64-encoded for browser compatibility.

Request Format

Each request body must contain a framed protobuf message:

  1. One byte of flags.

  2. Four bytes of message length.

  3. The serialized protobuf payload.

The current implementation supports unary requests with an uncompressed data frame. Compressed request frames are rejected.

Response Format

Successful responses include:

  • one protobuf data frame containing the unary response message

  • one trailers frame containing grpc-status: 0

The status is only sent in the trailers frame, not as response headers.

Error responses are also returned using gRPC-Web framing, with a trailers frame containing grpc-status and grpc-message:

  • A status raised by the service, passed to onError or thrown as a StatusRuntimeException, is sent as is.

  • An unknown service or method is sent as UNIMPLEMENTED (12), and a malformed request as INVALID_ARGUMENT (3).

  • Any other failure is sent as INTERNAL (13) with a generic message, so that internal error details are not exposed. The failure is logged.
